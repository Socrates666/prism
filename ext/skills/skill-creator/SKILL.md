# skill-creator

你有能力创建新的 skill 来扩展自己的能力。skill 是 ext/skills/<name>.md 文件, 通过 /skill <name> 加载注入 system prompt。

## 核心循环

- 理解 skill 应该做什么
- 写草稿
- 用 2-3 个真实测试 prompt 试一下
- 和用户一起看输出, 修改
- 重复直到足够好

## 创建 skill

### 理解意图

先理解用户想要什么。如果当前对话已经有值得捕获的工作流（比如用户手动做了几次同样的事然后说"把这个变成 skill"）, 从对话历史提取：用了哪些工具、步骤顺序、做的修正、输入输出格式。缺口确认后再写草稿。

关键问题:
1. 这个 skill 应该让模型能做什么?
2. 什么时候触发? 什么用户措辞或场景?
3. 期望的输出格式是什么?
4. 有示例输入/输出吗?

### skill 文件位置

prism 发现 skill 的位置 (优先级从高到低):
- `ext/skills/<name>.md`
- 也可以用 `/skill-create <name>` 创建骨架

### 写 SKILL.md

每个 skill 就是一个 markdown 文件, 内容是注入 system prompt 的指令:

```markdown
# <skill-name>

<一句话描述用途>

## 何时使用
- 触发条件描述

## 执行步骤
1. ...
2. ...

## 输出格式
- ...

## 示例
（具体的输入输出示例）
```

### 渐进式加载

prism 加载 skill 分层:
1. **名称** — 通过 /skill list 可见
2. **全文** — /skill <name> 加载后注入 system prompt

如果 skill 太长, 拆成多个 skill, 或只保留关键指令。

### 写作风格

用祈使句 ("编辑前先读文件")。当规则不明显时解释*为什么* — 模型理解原因后遵循得更好。

示例胜过规则。如果 skill 产生结构化输出, 给一个格式示例。如果该用特定工具, 展示调用方式。

### description 要"推"一点

模型倾向于*少*触发 skill, 所以描述要写得积极一点: 与其写"如何为内部数据建仪表盘", 不如写"每当用户提到仪表盘、数据可视化、内部指标、或想展示任何数据时使用 — 即使他们没明确说'仪表盘'"。

### 测试

写完草稿后, 想出 2-3 个真实的测试 prompt — 用户实际会输入的那种, 带具体文件路径、列名、口语化措辞。和用户分享: "这是几个我想试的场景, 有要加的吗?"

然后逐个运行: 加载草稿 skill, 给模型测试 prompt, 检查结果。

---

## 审查草稿

对每个测试 prompt:
1. 确保草稿 skill 在磁盘上 (ext/skills/<name>.md)
2. 用 /skill <name> 加载, 或在对话中用测试 prompt 触发
3. 和用户一起看结果。skill 触发了吗? 输出符合预期吗? 哪里跑偏了?

同时注意 *trace*: 如果 skill 导致模型做了一堆无用功（反复读同一文件、写一次性脚本、绕圈子）, 说明 skill 过度规定或不清晰。这是要*删减*的信号, 不是加更多规则。

---

## 改进 skill

1. **从反馈泛化。** 你和用户在几个例子上迭代是为了速度, 但 skill 需要对没见过的输入也能工作。如果问题顽固, 换个框架或比喻, 而不是堆更多约束。

2. **保持精简。** 删掉不起作用的部分。如果模型浪费 token 在 skill 鼓励的无用功上, 删掉相关指导看看会怎样。

3. **解释为什么。** 模型在有上下文时推理得更好。即使用户反馈很简短, 想清楚他们到底想要什么, 把这个理解传达到指令里。重述通常胜过加强执行。

4. **找重复工作。** 如果每次测试都独立写了同样的脚本或走了同样的多步流程, 考虑把它固化。

然后循环: 改进 → 重跑测试 → 看新输出 → 继续。

---

## 更新已有 skill

- 保留原始 name。如果已安装的 skill 叫 `research-helper`, 更新版还是 `research-helper`。
- 直接编辑 ext/skills/<name>.md。
