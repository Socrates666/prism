# TreeScribe · 小模型导航

> 本篇回答:**scribe 怎么导航搜索树、连续调用怎么扛延迟、谁控制搜索。**

## 一句话

**驻场小模型,每次请求前跑树搜索,把相关子树载入 prompt。树是唯一真实来源,prompt 是 scribe 算出的视图(view)。**

```
认知树(SQLite Forest)  ──TreeScribe 搜索──▶  search-state prompt ──▶  主模型
       ▲                                                            │
       └──── emit 产生新节点(CognitiveHook 自动挂树)◀──────────────┘
```

> 注意:对**搜索树**,scribe 拼的不是"选 context",是 **search-state**(根→frontier 决策路径 + 失败兄弟支 + 当前上下文 → "你在这一这试过不行,继续 or 回溯")。详见 [cycle.md](cycle.md)。

## 对比现有 context 方案

| 方案 | 任务隔离 | 结构意识 | spawn 递归表达 | 可解释路径 | 无限历史 | token 成本 |
|------|:------:|:--------:|:--------------:|:----------:|:--------:|:----------:|
| Last N(现状) | ✗ | ✗ | ✗ | ✗ | ✗ | O(N) |
| RAG 向量召回 | △ | ✗ | ✗ | ✗ | ✓ | 召回不精确 |
| Mem0(事实抽取) | △ | ✗ | ✗ | ✗ | ✓ | 平面事实表 |
| **TreeScribe** | **✓(按树)** | **✓(type/relation)** | **✓(causes 子树)** | **✓(树路径)** | **✓** | **O(相关子树)** |

## 连续调用性能(R2 落地)

- **`_context_sufficient()` 快速路径**:同一轮内连续工具调用(无新认知事件),不重触发 scribe,直接复用 `active_context` 缓存。小模型只在该轮首个请求 / 检测到新节点时跑一次。
- **`active_context` 跨调用缓存**:scribe 算出的视图缓存到下次认知事件为止。

## 默认笨 + 智能升级(对齐 MemoryBackend 套路)

| | 触发 | 实现 |
|---|---|---|
| **默认笨搜索**(core 自带) | 每次 loop | recency + 深度启发式,**无模型**,保证"超上下文"开箱即用 = 稳定能力 |
| **智能 scribe**(ext/ 升级) | 每次 loop | 小模型选最相关子树 = 升级 |

拔了 ext/,还是超上下文(笨的);插上,变聪明。这也让"直觉到底强不强"能 A/B 测(笨=对照组,智能=待验证假设)。

## 【open · round 8 α/β】谁控制搜索?

"标记 failed、回溯到父节点"谁干?(决定 agent_loop 整个怎么写)

| | (α) 主模型控制 | (β) 小模型控制 |
|---|---|---|
| 搜索器 | 主模型(读 search-state,自己决定标 failed/回溯/继续) | **小模型**(评估分支、决定探索/回溯,像搜索算法 evaluation function) |
| 主模型角色 | 搜索器 + 思考者 | 只在 frontier **生成下一个 thought** |
| 小模型角色 | 状态组装(导航员) | **搜索大脑**(主导) |
| 性质 | 主模型主导、小模型辅助 | 小模型主导(它才是"直觉"),主模型降级成生成器 |

**这两种是根本不同的 agent。** 未定。用户 round 8 例子里"模型标记失败回溯"的"模型"是哪个,需澄清。

## 【open】小模型选型与延迟(方案成立硬门槛)

方案成立前提:**scribe 推理时间 < 省下的 token 传输时间**。**必须实测**。

glm 系列小模型(glm-4.5-air 级)单次树搜索若 < 300ms 且省 token > 数千,净赚。若算不过账 → R2 退回纯启发式评分(不调模型)也能用(降级安全阀)。

## 【open】任务边界判定

LLM 判定新任务 vs 延续:新任务 → 新树根;延续 → 挂当前树。误判兜底 `/task new` 手动切。
